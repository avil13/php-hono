# Этапы, зависимости и оценка

Обновление 10 ноября 2026: выбранный объём 1.0 реализован; [приёмка и результаты T01–T32](implementation-status.md). Оценки ниже исторические, не фактический табель работы. Версия 0.1 отдельно не выпускалась, внешняя публикация 1.0 остаётся отдельным действием.

## Как читать оценку

Одна задача — самостоятельный проверяемый результат для одного PR либо небольшой последовательности PR. В оценку входят реализация, собственные тесты, review corrections и связанная документация. Человеко-день — примерно 6 часов сосредоточенной инженерной работы. Исследование и создание этого плана не включены.

Предполагается разработчик, знакомый с PHP и HTTP; greenfield-проект; объём строго по [спецификации](02-specification.md). Диапазоны не получены из существующей реализации — это предварительная инженерная оценка. После T02, T10 и MVP её необходимо пересчитать.

T21 перенесена в MVP по требованию использовать готовые сторонние middleware; ID сохранён, задача выполняется до T19. 2 ноября 2026 года в T06 добавлены типизированные extensions и DI-примеры: оценка изменена с 2–3 на 3–4 дня. В T08/T10/T19/T21 уточнены проверки, T20 включает руководство, T29 — lifecycle сервисов. T01 теперь включает Mago, строгую конфигурацию и read-only проверку staged snapshot: оценка 1–3 вместо 1–2 дней. Общее количество задач остаётся 32; относительно исходного плана нижняя граница суммарной оценки выросла на один день, верхняя — на два. Собственный DI-контейнер, autowiring и context factory в эти оценки не входят.

Резерв 25% на неизвестные совместимости и интеграции даёт **39–69 человеко-дней до MVP**, **60–109 до 1.0 суммарно** (округление вверх). Для одного разработчика при пяти рабочих днях в неделю это приблизительно **8–14 недель** и **12–22 недели**. Это не календарное обязательство: доступность инфраструктуры и review может увеличить длительность.

Для двух разработчиков суммарные человеко-дни не делятся автоматически пополам. Параллелить можно HTTP-модель и routing, затем независимые middleware; интеграция и фиксация контракта остаются последовательными. Отдельную календарную оценку для команды давать после назначения исполнителей и завершения T02.

## Порядок выполнения

1. T01 → T02: определить инструментальную базу, exact fixtures, поддерживаемый regex профиль, body limit и HTTP defaults.
2. Параллельно T03 → T04 → T05 и T07; T06 после T03/T04, включая typed extensions. T08 развивается поверх T07 и принимает готовые handlers с constructor injection.
3. T09 после T06/T07, T10 после T05/T08/T09: получить end-to-end dispatch в памяти на PSR messages.
4. T11 и T12 можно вести параллельно. После T10/T12 выполнить T21 с реальными PSR-15 пакетами. T14 развивать рядом с adapter; затем T13, T15–T18 по зависимостям карточек.
5. T19 интегрирует весь MVP, включая обязательный результат T21; T20 выпускает пилотную версию и фиксирует результаты.
6. После MVP параллелить T22, T24, T26, T27. T23 требует cookies/CORS, T25 — согласованного взаимодействия с ETag.
7. T28 и T29 могут выполняться независимо после MVP; совместная проверка обязательна в T31. T30 измеряет итоговый pipeline с worker.
8. T31 → T32 закрывают 1.0; задачи этапа M6 также обязательны к T31.

Полные непосредственные зависимости указаны в карточках. Этапы — продуктовые контрольные точки, а не запрет на раннюю независимую работу. Самая длинная цепочка MVP по верхним оценкам: T01 → T02 → T03 → T04 → T06 → T09 → T10 → T12 → T15 → T13 → T19 → T20 (32 человеко-дня без резерва). Это нижняя граница календарного планирования при идеальной параллельности; распределение исполнителей и пересмотр оценок могут изменить критический путь.

## Условия завершения этапов

- **M0:** Mago/pre-commit/CI проверены на PHP 8.5, SHA и classifications зафиксированы, regeneration воспроизводим, спорные defaults получили конкретные значения; не начинать совместимость с rolling docs.
- **M2:** `$app->handle($request)` возвращает корректный ответ для routing/middleware/error/HEAD сценариев; unit и contract tests этих контрактов проходят.
- **MVP:** все T01–T21 завершены; реальные сторонние PSR-15 middleware, типизированные Context extensions и явное отображение attributes прошли интеграционные тесты; constructor injection и необязательный PSR-11 bootstrap документированы; нет необъяснённых расхождений supported profile; PHP 8.5/FPM пример работает; ограничения multipart, маршрутов и bridge опубликованы.
- **1.0:** все 32 задачи завершены; streaming/worker проверены на реальном runtime; публичный API стабилен, известных блокирующих ошибок нет. Выпуск 1.0 не переименовывать в «полный Hono parity».

## Риски, влияющие на сроки

| Риск | Действие в плане |
| --- | --- |
| Документация v5 смешивается с кодом v4 | Pin SHA, T02 manifest, обновлять baseline отдельно |
| Тонкие различия ordering/next/headers | Сначала fixtures, затем T09/T10 и integrated T19 |
| PSR-15 interface не гарантирует совместимость поведения каждого пакета | T21: реальные packages плюс contract tests body/attributes/errors; ограничения retry/rewrite/error boundaries описаны |
| PHP меняет query/form keys и теряет multipart duplicates | Собственный небольшой query/urlencoded parser; SAPI multipart divergence; полный parser отдельно |
| PCRE не равен JS RegExp | Ограниченный общий профиль, отказ на unsupported, adversarial fixtures |
| Middleware body limit срабатывает после SAPI buffering | PHP/web server limits + отдельные adapter tests, без ложной гарантии раннего контроля |
| Утечки состояния/памяти в workers | Request-scoped extensions/factories, T29 последовательные запросы/ошибки, cleanup и длительный прогон; новый Context не очищает общие сервисы внешнего контейнера |
| Streaming + output buffering + exception | Выделенный контракт, тесты реального emitter/proxy, не обещать post-header replacement |
| Ожидание скорости Hono | T30 benchmark; никаких численных обещаний до измерений |
| Зависимости или инструменты не готовы к PHP 8.5 | Проверить в T01; выбирать поддерживаемые релизы, не понижать PHP без нового решения пользователя |
| Рост scope до «всего upstream» | Пересчитать план; не прятать отдельные подсистемы внутри текущих 32 задач |

## Направления после 1.0 — неоценённые эпики

Эти пункты **не входят в 32 задачи и оценки**. Каждый требует отдельной спецификации и дробления перед началом:

1. Полная route grammar Hono, mount/host routing и дополнительные router presets при доказанной пользе.
2. Multipart из raw bytes для произвольных методов, сохранение повторов, `all/dot`, безопасные лимиты вложенности и файлов.
3. JWT/JWK и signed cookies через проверенные библиотеки; IP restriction и trusted proxy policy.
4. Cache через PHP cache adapter, proxy/PSR-18 и remaining HTTP helpers (accepts/language/timing/combine/method override/pretty JSON).
5. Дополнительные runtimes, async/Fiber scope и timeout/cancellation.
6. OpenAPI/client generation; PHP type metadata не объявлять эквивалентом `hc<AppType>`.
7. Интеграция PHP-шаблонов и независимый SSG при подтверждённом спросе.

**JSX и WebSocket исключены из всего проекта по требованию пользователя. Они не являются будущими эпиками.** HTTP streaming/SSE остаются в T28.

Полный порт всех exports Hono — другая оценка проекта. Этот план даёт законченное HTTP-ядро и выбранный набор расширений с проверяемыми границами.
